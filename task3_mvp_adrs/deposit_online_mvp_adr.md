### <a name="_qmphm5d6rvi3"></a>**Решение**
Диаграмма контекста для MVP онлайн депозитов: [puml](deposit_online_mvp_c4_context.puml) | [png](deposit_online_mvp_c4_context.png).

Диаграмма компонентов для MVP онлайн депозитов: [puml](deposit_online_mvp_c4_containers.puml) | [png](deposit_online_mvp_c4_containers.png).

Логика принятия решений:
- Функционал работы с депозитами планируется добавить и перенести в новый сервис, включая миграцию имеющихся данных из АБС.
- Есть проблемы с АБС:
    - она сосредоточила в себе много функций, при этом уже есть сложности с производительностью;
    - технологии при помощи которых реализована АБС создают риск потери поддержки;
- Новый сервис планируется реализовать с использованием знакомых командам технологий: Java/С#, React, MS SQL/Oracle. Вариативность обусловлена неочевидностью исполнителей, которые будут определены в зависимости от уровня нагрузки.
- Информацию о ставках планируется хранить в БД нового сервиса.
- Начинаем плавно переводить интернет-банк на микросервисную архитектуру используя StranglerFig, подробности на диаграмме: [puml](online_banking_c4_component.puml) | [png](online_banking_c4_component.png). Это позволит добавить СМС-подтверждения в интернет-банке без модификации ядра подрядчиком.
- Вспомогательная информация для расчета ставок по-прежнему может быть получена депозитным менеджером.
- Данное решение подразумевает высокую нагрузку на команды разработки оправданную не только текущими (MVP), но и годовыми целями.
- Предложенный вариант реализации создает хороший задел для реализации годовых планов.
- Все новые сервисы должны быть написаны с учетом готовности к масштабированию (stateless, отсутствие привязки к экземпляру и т.д.).
- Все новые сервисы должны развертываться в платформе оркестрации для оперативного масштабирования и обеспечения требований к надежности.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Альтернативные варианты предусматривают управление нагрузкой на разработку и управление рисками.

- Консервативное решение: реализовать все операции с депозитами в АБС. Оно позволяет снизить сложность разработки MVP, однако несет в себе риски перегрузки систем и сложности реализации годового плана.

- Максимальное решение: обновление ИТ-структуры для динамичного развития в будущем. Помимо нововведений из основном варианта, включает внедрение Event Driven подхода на основе Kafka. Этот вариант позволяет снизить зависимость между сервисами, упростив разработку, обновление и развертывание.

### <a name="_bqtru6e2h5dx"></a>**Недостатки, ограничения, риски**
Недостатки:
- Менеджерам депозитного отдела бэк-офиса придется научиться работать в новом интерфейсе сервиса депозитов.
- Высокая сложность разработки из-за старта нового сервиса депозитов и переноса в него соответствующего функционала из АБС (включая миграцию данных).

Ограничения:
- Для межсервисных взаимодействий осознанно не использованы брокеры сообщений с целью снизить сложность и без того непростой разработки. Взаимодействия между сервисами происходит при помощи синхронные технологии (HTTP/GRPC), что ограничивает транзакционность, усиливает связи между сервисами.

Риски:
- Ошибки при переносе функционала и данных работы с депозитами из АБС в новый сервис.
- Пропуск сроков MVP.
