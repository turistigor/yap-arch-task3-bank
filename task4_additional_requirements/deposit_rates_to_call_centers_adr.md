### <a name="_qmphm5d6rvi3"></a>**Решение**
Диаграмма контекста: [puml](deposit_rates_to_call_centers_c4_context.puml) | [png](deposit_rates_to_call_centers_c4_context.png)

Диаграмма контейнеров: [puml](deposit_rates_to_call_centers_c4_containers.puml) | [png](deposit_rates_to_call_centers_c4_containers.png)

Логика принятия решений:
- Ставки по депозитам для новых клиентов могут быть получены оператором любого кол-центра через сайт. Решение тривиальное, на схеме не отображено для читаемости.
- Ставки по депозитам для существующих клиентов могут быть получены сотрудником кол-центра банка через систему кол-центра. Данный функционал должен быть реализован в системе кол-центра (согласно условию для этого есть возможность) при помощи прямого API-вызова нового сервиса депозитов. Данное решение является продолжением идеи о том, что в MVP онлайн депозитов планируется синхронное общение между сервисами.
- Ставки по депозитам для существующих клиентов могут быть получены сотрудником партнёрского кол-центра на SFTP-сервере. Скорее всего это будет внешний сервер так как своего у банка сейчас нет, а его развертывание несет риски срыва сроков MVP в случае задержек. Файлы со ставками будут выгружаться на сервер сервисом депозитов при любом изменении. Чтобы этот процесс не стал блокером для обработки запросов на изменение депозитов, планируется использовать асинхронную очередь задач (Spring Batch или Hangfire в зависимости от языка реализации сервиса).

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
- Ставки по депозитам для существующих клиентов могут быть получены сотрудником кол-центра банка не через систему кол-центра, а через интерфейс сервиса депозитов. Это вариант на случай, если окажется, что доработать систему кол-центра не получится.
- SFTP-сервер может быть внутренним, если для этого будут возможности, либо партнёрским, если таковой имеется.

### <a name="_bqtru6e2h5dx"></a>**Недостатки, ограничения, риски**
Недостатки:
- Синхронное общение между сервисами увеличивает связность сервисов.

Ограничения:
- Использование SFTP-сервера ограничивает оперативность доставки свежих изменений в партнёрскую систему.

Риски:
- Использование асинхронной очереди задач повышает риски неконсистентности данных между системами в случае ошибок.
- В случае отказа SFTP-сервера партнёрский сервис не сможет эффективно принимать на себя операционную нагрузку.
